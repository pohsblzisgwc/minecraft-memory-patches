# 服务端内存问题：转储观测、代码分析与修复

## 范围与证据分级

本次关注三条玩家引用滞留路径、一个高频分配问题和一个数据库故障积压问题。刻意保留的游戏机制和正常缓存不作改造。五个补丁相互独立。

以下明确区分三类依据：

1. **转储观测**：来自两份相隔约 25 分钟的原始堆分析记录。样本 A 在 GC 后获取，样本 B 未强制 GC。这里只公开聚合数量，不公开原始文件、地址、玩家标识、世界位置或 GC Root 中的业务值。
2. **理论/代码分析**：针对现场版本的字节码、引用关系和控制流程，判断是否存在持有或分配机制。它解释可能因果，不等于每一条生产调用路径都已实测。
3. **回归实测**：在隔离 Fabric 服务端或临时 SQLite 文件上验证具体不变量。初版测试遗漏的问题通过补充测试发现并修复。

后续审查没有独立重新解析两份完整转储。因此，原始聚合数值属于“已记录的转储分析”，不是后续审查逐项复算所得；当前补丁行为和补充回归则是直接实测结果。

## 转储中的整体情况

| 聚合指标 | 样本 A | 样本 B | 解释 |
| --- | --- | --- | --- |
| 已移除但仍被引用的玩家对象 | 594 | 599 | 存在持续滞留，但两个快照不足以给出长期增长率 |
| 指向已移除玩家的地图 HoldingPlayer | 14,825 | 14,993 | 数量明显超过在线玩家需求，需检查清理路径 |
| Ledger 排队动作 | 748 | 10,639 | 与数据库错误、消费停滞相吻合 |
| 已移除玩家关联对象的估算保留大小 | 约 446 MiB | 约 450 MiB | 非 JVM 实测值；字段布局和引用语义存在估算误差 |

两个样本 GC 条件不同，文件体积或不可达对象增量不能直接解释为真实存活堆增长。原分析在未强制 GC 样本中记录了约 3 GiB 的大 int[]，大部分没有入向引用，并呈现 G1 Region 填充的对齐特征。这支持“很多是 GC 填充/已死亡区域”的解释，不能仅凭直方图把它们算作模组泄露，也不应宣称每个大数组的来源均已百分之百证实。

原分析还记录了约 241 万个不可达 LinkedHashMap 节点，HPROF 口径约 147 MiB。结合 ConfluxMap 的轮询循环，存在明确的高频拆建机制；未进行分配栈采样前，不把所有死亡节点都严格归因给单一调用点。

## 问题一：地图持有人滞留已移除玩家

**转储观测**：地图存档对象通过 HoldingPlayer 持有大量已移除玩家，进而保留进度、实体交互等关联对象。一个玩家可以同时被多张地图持有，不能把每个 HoldingPlayer 当成独立玩家计数。

**代码分析**：Lithium 的展示框地图快速路径把原版对 carriedBy 的遍历替换为只处理当前玩家，因而不再巡检其他已移除持有人。仅依赖后续原版遍历的清理策略在此路径下失效。

**修复方案**：给玩家增加到地图的弱引用反向索引；Entity.setRemoved 后定向清除对应 HoldingPlayer 和玩家标记；tickCarriedBy 入口阻止已移除玩家重新入表；展示框路径增加有限步数游标巡检。工作线程触发的主动清理调度回服务端主线程。

**实测与边界**：假人退出后 carriedBy 与 carriedByPlayers 清空；再次用已移除玩家触发 tick 不会回漏。尚未覆盖所有模组组合下的并发地图调用、重生和跨维度路径；不能把反向索引上的锁解释为所有地图容器都线程安全。

## 问题二：假人断开未注销 Fabric 网络状态

**转储观测**：GlobalReceiverRegistry 的会话集合持有已断开的假人网络附加对象。地图引用与网络引用可能同时指向同一个玩家，不能把两条路径的估算内存简单相加。

**代码分析**：Carpet 的 FakeClientConnection 使用未按真实网络方式挂载 pipeline 的 EmbeddedChannel，并绕过普通连接的断开处理。依赖 Netty channelInactive 的 Fabric 注销逻辑因此可能不执行。

**修复方案**：在服务端游戏监听器 onDisconnect 尾部识别假连接，调用 Fabric 标准 handleDisconnect；保留其 AtomicBoolean 幂等事件保护。以 finally 保证 endSession 和通道关闭，事件监听器抛异常时仍完成必要清理，异常继续向调用者传播。

**实测与边界**：正常断开时 DISCONNECT 事件发生，trackedAddons 回到基线；主动抛异常的监听器不再阻止注销和通道关闭，重复调用不重复派发事件。公开记录只展示断言结果，不公开原始连接日志。

## 问题三：TIS 弹射物 ThreadLocal 强持有实体

**转储观测**：工作线程的日志上下文指向弹射物，弹射物再经命中和伤害引用链保留其他实体及玩家。

**代码分析**：TIS 在 Projectile 基类构造时无条件保存 currentEntity，但 Carpet 只在日志开启且为部分子类时创建消费该上下文的 TrajectoryLogHelper。日志关闭或不支持的子类容易留下值；对象换线程入世后，在主线程调用 remove 不能清理构造线程的 ThreadLocal。

**初版遗漏**：日志关闭路径虽通过，但日志开启、工作线程构造烟花、主线程入世时仍复现原线程遗留。只增加 tick/addFreshEntity 边界不能完整解决。

**当前修复**：替换上下文容器，只有开启日志的 AbstractArrow / ThrowableProjectile 保存弱引用；其他类型不保留实体。构造期间日志 helper 仍能取得原实体；异常或未消费的构造不再由此 ThreadLocal 强持有对象，不依赖其他线程清理。

**实测与边界**：跨线程烟花无遗留；Arrow 和 Snowball 的 helper.entity 与原实体同一对象；没有入世且没有 helper 的 Arrow，在外部放弃引用后可被回收。异常构造防滞留依据弱引用设计，未对每一种构造异常注入测试。

## 问题四：ConfluxMap 状态轮询制造高频垃圾

**转储观测**：存在大量死亡 LinkedHashMap 节点及相关短命对象；更接近分配抖动，而非同量对象永久存活。

**代码分析**：refreshLevels 每 tick 最多检查 2048 项，每项执行 LinkedHashSet 的 remove/add 旋转；在 20 TPS 且队列足够大时理论上可达每秒 40,960 次。未变化的 ticket 还重复构建 Optional、状态、捕获 lambda、发布键和值。

**修复方案**：使用 ArrayList 游标环和分维度位置索引；缓存每 tick 的维度编号及上次已发布 ticket；只在变化时发布。卸载使用交换删除，最后一项卸载后移除空维度桶，clear 同步清空索引。多订阅者仍保留公平轮转。

**测试补强**：初版只检查数量，不能证明“exact parity”。当前逐项核对发布键、坐标、ticket、band；验证两个订阅者的完整快照和缓存等级刷新增量；用 2125 项测试首 tick 的 2048 项预算与下一 tick 覆盖余项，以及卸载重载和清空。

**边界**：轮转测试含合成的未加载区块，不等同于 2125 个真实区块的长期压力测试。缓存刷新通过模拟先前发布状态验证，没有调用 C2ME 禁止的 setTicketLevel。尚不承诺动态维度重新编号的所有场景。

## 问题五：Ledger 数据库异常和无界队列

**转储及日志观测**：队列从 748 增至 10,639；分析记录中的 SQLite 缺表错误与事务重试说明消费出现阻塞。原始数据库和错误日志均不公开。

**代码分析**：默认 LinkedBlockingQueue 无容量上限；数据库重试期间生产端仍入队。初版 size 检查与后续 add 分离，多个线程可同时通过；补充测试在容量 25 时观察到 26，属于有限并发超额，并不据此断言仍会无限增长。

**队列修复**：Redirect 原 add 调用，在同一生产者锁内完成检查、必要淘汰及实际入队；消费者只能减小队列。默认丢新动作，可配置丢旧动作。容量控制的是条目数，不是固定字节数；满队列会丢失审计信息。

**小库恢复**：在已获得重置授权的前提下，仅在启动打开默认连接前，检测到损坏/缺表/缺列，且主文件与 WAL、rollback journal 合计严格小于 10,000 字节时恢复。先保留旧文件及侧文件备份，再让 Ledger 自身创建完整 schema 和缓存；健康小库、较大库、忙锁/权限/I/O 错误和符号链接不触发重置。运行中不热删除，下一次启动检查。

**实测**：两种丢弃策略分别以 32 线程运行 500 轮，上限及峰值均为 25，零超限，保留动作身份和顺序符合策略。28 项恢复断言覆盖严格阈值、健康库、缺表/列、WAL 数据、锁与备份。两轮真实隔离服从损坏文件和缺表文件完成备份、建表、读写及全部回归。

## 对原分析结论的修正与验证策略

自定义堆解析器按字段总大小推算实例大小，未完整模拟 JVM 字段填充；部分图遍历把 Reference.referent 当作普通强边。因此“JVM 实际”“精确保留大小”应改成有假设的估算。上述误差不自动推翻已找到的具体强引用路径，但会影响节省内存的量化承诺。

G1 默认使用自适应 IHOP，不能把启动参数的 15% 当作长期固定阈值；Oracle GraalVM 删除 EnableJVMCI 参数也不保证改用 C2。代码修复与 JVM 调参应分开，在同类负载下对比 GC 后存活堆、暂停、分配率、队列长度和引用集合基线。不要同时更改大量参数后把全部变化归给补丁。

参考：[Oracle JDK 25 G1](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html)、[GraalVM 编译器选项](https://www.graalvm.org/latest/reference-manual/java/options/)、[SQLite WAL](https://sqlite.org/wal.html)。

## 补充更正：ConfluxMap实测与GC统计口径

后续复测与统计口径说明见 [ConfluxMap复测补充](CONFLUX_RECHECK.zh-CN.md)。本节作为追加说明，保留前文与提交历史。

- 原记录可核对的约147.49/411.72 MiB是约35.8%的快照死对象估算字节比例，不是GC耗时比例；“GC的44%”缺少可核对的分母和时间测量，不作为结论。
- 受控稳态实验中，原版每tick检查2048项约分配144 KiB，按20 TPS折算2.81 MiB/s；本机组件耗时约0.18 ms/tick。现有补丁显著降低此路径分配，但组件耗时也不能用来推算GC耗时。
- 0.1.12、0.1.16和0.1.17-rc.1的三个相关核心class相同，较新原版未优化该轮转算法。另复现无地图需求时已卸载键的延迟清理，现有补丁未覆盖该队列问题。
- 本次没有测量生产GC暂停收益，也不证明生产已部署补丁。
